## 0. 背景

F-01（停止した店舗・削除したユーザーの扱い）の E2E を進める中で、次の3件を F-01 の範囲外として記録した（`docs/E2E-F01-RUNBOOK.md` の10章、`docs/PLAN-test-db-isolation.md` の Step 4-13）。本番公開の前に扱う。

1. 自己登録で ADMIN のユーザーができる。
2. 承認されていない店舗が、市場データを見られる。
3. `proxy.ts` が、JWT の role で判定している。

## 1. Phase 1：調査結果（2026-11-27。コードを読んだだけ。DB・開発サーバーは使っていない）

### 1-1. 自己登録で ADMIN ができる（確認済み）

- `/register` は、`proxy.ts` の `publicRoutes` に入っていて、ログインしていなくても開ける。トップページ（`app/[locale]/page.tsx:33`）とログイン画面（`app/[locale]/login/page.tsx:142`）からリンクがある。
- `actions/auth/register.ts` の `registerUser` は、新しい `Shop` と `User` を1つのトランザクションで作る。**`role: UserRole.ADMIN` を指定している**（52行目）。スキーマの既定値は `STORE`（`prisma/schema.prisma` の `User.role`）。
- `registerUser` は Server Action なので、画面を消しても、POST で直接呼べる。**登録を止めるときは、Server Action の中で止める必要がある。**
- CLAUDE.md では、ADMIN は KatanaService の管理者（店舗・ユーザー・マスタ・運用の管理）を指す。
- **今の影響：** ADMIN だけが使える画面や処理は、まだない（`app` の中に `admin` のページはない。`lib/auth/context.ts` の `hasRole` は、どこからも使われていない）。今は実害がないが、管理者の機能を作った時点で穴になる。

### 1-2. 承認されていない店舗が市場データを見られる（確認済み。最も影響が大きい）

- 承認の仕組みがない。`Shop.isActive` の既定値は `true` で、`registerUser` も値を指定しないので、登録した直後から有効な店舗になる。
- ログイン（`data/user.ts:25`）とダッシュボードの認可（`app/[locale]/dashboard/_lib/requireDashboardContext.ts` → `lib/auth/context.ts` の `getAuthContext`）は、`isActive` だけを見る。
- そのため、誰でも登録するだけで、次のことができる。
  - 参加している店舗の市場データ（在庫数・平均・中央値・SOLD 数・価格の推移）を見る。
  - 自分の商品を取り込み、市場データに混ぜる。市場の集計の条件は `shop: { isActive: true }` だけ（`lib/market-analytics/currentMetrics.ts:13`・`:27`、`lib/market-analytics/priceTrend.ts:40` など）。
- 長く積み上げる市場データがサービスの価値なので、データを汚せることの影響が大きい。
- **無効の店舗は、すでに市場の集計から外れる**（上の条件）。ログインもできない（`data/user.ts:25`）。

### 1-3. `proxy.ts` が JWT の role で判定している（確認済み）

- `proxy.ts:50-55` は、`/dashboard/admin` から始まる URL を、`req.auth.user.role`（JWT の値）で判定する。
- JWT の role は、ログインした時点の値のまま変わらない（`auth.config.ts:36-45` の `jwt` コールバックは、`user` があるときだけ書き込む）。DB で ADMIN を外しても、ログアウトするまで ADMIN として扱われる。F-01 の E2E-05 で見た「動作が変わらない」ことと同じ原因。
- `getAuthContext()` は、DB の最新の `role` を返すが、role で判定している場所はまだない。
- **今の影響：** `/dashboard/admin` のページがないので、実害はない。

### 1-4. 確かめていないこと

- 開発用DB に、自己登録で作られた ADMIN のユーザーが何人いるか（Phase 4 の最後の記録は User 2・Shop 2。2026-10-23 時点）。確かめるには、承認を得て DB に接続する必要がある。
- 本番の環境があるか、そこに自己登録のユーザーがいるか。

## 2. Phase 2：方針（2026-11-27。ユーザーが「おすすめの案」を選んだ）

**基本の考え方：** まず、小さい変更で穴をふさぐ。承認の流れと管理者の機能は、その後に別の工程で作る。今回は Prisma のスキーマを変えない。

| 件 | 決めたこと |
|---|---|
| 新しい店舗の受け付け | **当面は自己登録を止める。止め方は案 C-1（登録を閉じる）**（2026-11-27・ユーザーの判断。下の「自己登録の止め方」）。承認の流れ（自己登録＋管理者の承認、または管理者が作る招待制）は、管理者の機能と一緒に後で作る |
| 承認を待つ店舗のデータ | **市場の集計に入れない。** 承認の状態を持たない今の作りでは、「無効の店舗は集計から外れる」既存の条件で満たす |
| ADMIN の意味 | **KatanaService の運営者だけ**（CLAUDE.md のとおり）。店舗の中の管理者という役割は、今は作らない |
| 自己登録で作るユーザーの role | 登録を残す場合も、**必ず `STORE`**（多重の防御として、登録を止める場合も直しておく） |
| ADMIN の判定 | **サーバー側で、DB の最新の値（`getAuthContext()` の `role`）で行う。** `proxy.ts` の判定は、画面の振り分け（使いやすさ）のためだけに残し、認可の根拠にしない |

### 自己登録の止め方（2026-11-27。案 C-1 に決定）

検討した案は次のとおり。**ユーザーの判断で、案 C-1 にした。**

- **案 C-1（採用）：登録を閉じる。** `registerUser` は何も作らずにエラーを返す。`/register` は「現在、新規登録は受け付けていません」と表示する。トップページとログイン画面のリンクは消す。
  - 長所：DB に何も増えない。変更が小さい。
  - 短所：新しい店舗は、承認の流れができるまで、運営者が手作業で作る。
- **案 C-2（不採用）：登録は残し、無効の店舗として作る。** `role: STORE`・`isActive: false` で作り、運営者が DB で有効にする。
  - 長所：参加の申し込みを受け付けられる。
  - 短所：登録した人は、有効になるまでログインできない。今のログインは「パスワードが違う」と区別しないので、利用者に分かりにくい（表示の変更が別に要る）。承認されない店舗のデータが溜まる。

### まだ決めていないこと

1. **最初の ADMIN の作り方：** 管理者の機能を作るときまで決めなくてよい（今は ADMIN だけの機能がない）。
2. **開発用DB の既存のユーザーの扱い：** 自己登録で作られた ADMIN を `STORE` に直すか。確かめるには DB への接続（承認が必要）が要る。今回の変更には含めない。

## 3. Phase 3：実装の順序（案。まだ実施しない）

各 Step は、承認を得てから行う。Step ごとに、名前を指定した、DB を使わないテストだけを実行する。

### Step 3-1：自己登録の role を `STORE` にする

- **作業内容:** `actions/auth/register.ts` の `role: UserRole.ADMIN` を `UserRole.STORE` にする（または指定を消して既定値に任せる。どちらにするかは実施時に決める）。
- **テスト:** `registerUser` の単体テストを新しく作る（Prisma はモック）。作られる `User` の `role` が `STORE` であることを確かめる。
- **影響:** 登録の結果が変わるだけ。今は ADMIN だけの機能がないので、利用者に見える違いはない。

### Step 3-2：自己登録を止める（案 C-1）

- **作業内容:**
  - `registerUser` の先頭で、何も作らずにエラーを返す（Server Action を直接呼ばれても止まるように、画面ではなくサーバー側で止める）。
  - `/register` の画面を、受け付けていない旨の表示に変える。
  - トップページとログイン画面の登録へのリンクを消す。
- **テスト:** `registerUser` が DB に書き込まないこと（`prisma.shop.create`・`prisma.user.create`・`$transaction` が呼ばれないこと）を、モックで確かめる。
- **将来、登録を再開するときの扱い:** 定数や環境変数で切り替えられるようにはしない（承認の流れを作るときに、改めて実装する）。

### Step 3-3：ADMIN の判定をサーバー側に用意する

- **作業内容:** `lib/auth/context.ts` に、DB の最新の role で ADMIN を確かめる関数（例：`requireAdminContext`。名前は実施時に決める）を加える。`getAuthContext()` が失敗するとき・role が `ADMIN` でないときは拒否する。
  - 今は使う場所がないので、関数とテストだけを用意し、管理者の機能を作るときに必ずこれを使うことを、本ファイルと `CLAUDE.md`（変更には承認が必要）に書く。
  - 使う場所がないまま関数を足すことに反対なら、この Step は「規則の明記だけ」にする。
- **`proxy.ts` について:** 判定は残す（JWT の role で、画面を早めに振り分けるだけ）。コメントで「認可の根拠ではない。ページと Server Action でサーバー側の判定を必ず行う」と明記する。
- **テスト:** 新しい関数の単体テスト（`auth()` と Prisma はモック）。DB で `STORE` に変えたユーザーは、JWT が ADMIN のままでも拒否されること。

### Step 3-4：文書の更新

- `docs/E2E-F01-RUNBOOK.md` の10章と、`docs/PLAN-test-db-isolation.md` の該当の記述に、対応の結果を書く。
- 本ファイルの状態を更新する。
